/goal 프로젝트 네이밍은 VibeOS 으로 하자.
폰트 크기는 가시성 있는 크기로 해줘.
UIUX 는 관련 전문가로서 네가 UI 프레임워크 추천해줘.
개발 완료되면 화면에서 오류 없이 돌아갈수 있게 해줘.

핵심은 단순한 “AI 코딩 툴”이 아니라, 여러 바이브코딩 프로젝트를 동시에 만들고, 평가하고, 버리고, 키우고, 공통 자산으로 재활용하게 해주는 운영체제에 가깝게 잡는 게 좋아 보여.

그러면 20개의 실패 프로젝트를 만든 사람이 20번 실패한 게 아니라 개인 개발 플랫폼을 구축한 것이 돼.

그리고 이것이 시간이 지나면 더 재미있어진다.


가능해. 다만 **“서버가 아예 없는 구조”**와 **“내가 운영하는 서버가 없는 구조”**는 구분하는 게 좋아. 네 서비스라면 후자가 현실적이고, GitHub 자체를 백엔드처럼 활용하면 된다.

### 1. 핵심 설계 원칙

가장 중요한 요구사항은 **브라우저에서 LLM API Key를 직접 사용하지 않는 것**이야.

OpenAI나 Anthropic 등의 API Key를 React 코드에 넣으면 결국 사용자에게 노출된다. GitHub도 토큰이나 credential을 클라이언트 코드나 repository에 저장하지 말 것을 권고한다. ([GitHub Docs][1])

따라서 무거운 분석은:

```text
Browser
   ↓
GitHub workflow 실행 요청
   ↓
GitHub Actions
   ↓
LLM API
   ↓
분석 결과 JSON 생성
   ↓
GitHub Repository commit
   ↓
Browser가 결과 조회
```

방식으로 만든다.

즉 **GitHub Actions가 사실상 Serverless Worker 역할**을 한다.

## 2. 데이터를 GitHub Repo 자체에 저장

별도의 PostgreSQL이나 Supabase를 만들지 말고 전용 repository 하나를 둬.

예를 들어:

```text
vibe-portfolio-data/

├── projects/
│   ├── clustara.json
│   ├── vibe-coders.json
│   ├── project-a.json
│   └── project-b.json
│
├── analysis/
│   ├── clustara/
│   │   ├── latest.json
│   │   └── history/
│   └── vibe-coders/
│
├── assets/
│   ├── auth.json
│   ├── llm-wrapper.json
│   └── ui-components.json
│
├── ideas/
│   └── inbox.json
│
└── portfolio/
    └── summary.json
```

그러면 데이터베이스가 필요 없어.

그리고 Git이 알아서:

* versioning
* history
* rollback
* synchronization
* backup
* diff

를 제공한다.

이 구조가 네 서비스 아이디어하고도 굉장히 잘 맞아.

**프로젝트의 역사가 곧 Git history**가 되니까.

# 4. Repository 분석 항목

| issues         | backlog    |
| stars/forks    | 외부 반응      |

이걸 가지고 우선:

```text

Prototype
Experiment
Grow
Maintain
Dormant

```

정도로 상태를 자동 분류하면 돼.

예를 들어 매일 새벽 혹은 사용자가 버튼을 누르면:

```text

```

workflow를 실행한다.

```mermaid
sequenceDiagram
```

GitHub Actions 내부에서는 built-in `GITHUB_TOKEN` 사용을 GitHub가 권장한다. 또한 Actions의 `GITHUB_TOKEN`은 repository 단위로 기본 API limit이 적용된다. ([GitHub Docs][2])

# 6. 브라우저는 읽기 중심

프론트에서는 가능한 한 이런 것만 한다.

```text
GitHub API 조회
        ↓
React 상태
        ↓
IndexedDB Cache
        ↓
Dashboard
```

그리고 Repository가 변경되었을 때만 다시 가져온다.

GitHub API를 계속 polling하면 좋지 않다. GitHub도 polling 대신 event 기반 접근을 권장하고 있고, API 호출에는 rate limit이 있다. 인증된 일반 사용자 요청은 일반적으로 시간당 5,000회 한도가 적용된다. ([GitHub Docs][3])

그래서 local cache가 중요하다.

# 7. 가장 까다로운 부분은 인증

여기가 이 아키텍처의 핵심 제약이야.

### 개인용 MVP

나는 처음에는 **Fine-grained PAT**가 제일 낫다고 봐.

사용자가 자기 GitHub에서 token을 하나 발급하고:

```text
VibeOS
 ↓
Token 입력
 ↓
Browser 저장
 ↓
GitHub API 직접 호출
```

하는 방식.

GitHub도 개인 API 사용에는 PAT을 사용할 수 있고 가능하면 fine-grained PAT을 권장한다. ([GitHub Docs][2])

초기 개발 단계라면 이것만으로 충분해.

# 9. 서비스가 커지면 인증만 별도화

여기서 재미있는 게 있어.

처음에는:

```text
GitHub Pages
+
PAT
+
GitHub Actions
```

만으로 간다.

사용자가 늘어나면:

```text
GitHub Pages
+
GitHub OAuth 또는 GitHub App
+
아주 작은 Auth Function
+
GitHub Actions
```

으로 넘어가면 돼.

GitHub OAuth의 client secret은 브라우저 코드에 포함하면 안 된다. GitHub도 client secret을 client-side 코드나 사용자 장치에서 실행되는 코드에 포함하지 말라고 명시하고 있다. ([GitHub Docs][3])

그래서 **완전한 멀티유저 SaaS를 만들면서 서버를 0개로 만드는 것**에는 인증 때문에 한계가 생겨.

## 그리고 한 단계 더 가면

GitHub가 단순 데이터 소스가 아니라 **이 서비스의 Runtime 자체**가 된다.

```mermaid
flowchart LR
    DEV[나] --> APP[Vibe Portfolio]

    APP --> GH[GitHub]

    GH --> CODE[Source Code]
    GH --> DATA[Project DB]
    GH --> JOB[GitHub Actions]
    GH --> HOST[GitHub Pages]
    GH --> HISTORY[Git History]

    JOB --> LLM[AI]

    LLM --> SCORE[Project Intelligence]
    SCORE --> DATA

    DATA --> APP

    style DEV fill:#d9eaf7
    style APP fill:#cfe2f3
    style GH fill:#fff2cc
    style CODE fill:#d9ead3
    style DATA fill:#d9ead3
    style JOB fill:#d9d2e9
    style HOST fill:#d9d2e9
    style HISTORY fill:#d9d2e9
    style LLM fill:#fce5cd
    style SCORE fill:#ead1dc
```

이 구조라면 **초기에는 AWS도, DB도, Kubernetes도, 서버 운영도 필요 없다.**

그리고 나는 이게 꽤 중요한 제품 철학이 될 수 있다고 봐.

**“VibeOS does not own your projects.”**

코드도 GitHub에 있고, 프로젝트 메타데이터도 GitHub에 있고, 분석 이력도 Git에 남아 있으니 **서비스가 없어져도 사용자의 데이터는 그대로 남는다.**

바이브코더를 위한 서비스라는 성격에도 상당히 잘 맞는 구조야. ([GitHub Docs][2])

다음 구현 단계라면 이제 **실제로 `vibe-portfolio` Repository 하나를 만든다는 전제로 디렉터리 구조 + JSON Schema + GitHub Actions YAML + React 화면 구성까지 개발 명세 수준으로 내려갈 수 있어.**
